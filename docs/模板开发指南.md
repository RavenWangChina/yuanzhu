# 模板开发指南——把你的工作流做成可安装的资产

> 你已经把项目跑起来了（没有？先看 [使用场景与接入形态](使用场景与接入形态.md) 的快速开始），
> 现在想让它干**你自己的**活。

## 零门槛路径：一句话铸造（推荐先试这个）

**不用写任何 YAML**。把你的工作场景用大白话说出来，AI 直接铸成模板，评测自动把关，全过即上架：

```bash
yuanzhu forge "我是部门主管，每天下午要让各小组组长提交今日工作进展和明日计划，我汇总成一份部门日报发给领导"
# ✅ 已上架: dept-daily-report（evals 2/2 通过）
```

Web 端同样可以：模板市场顶部的「铸造模板」输入框。铸出来的落在 `templates/forge/<域名>/`，
标准四段式目录——想微调就照着下面的指南改，改完重新注册即可。

评测没全过会留在草稿区（模板市场可见、不会误上架），报错会告诉你哪条用例挂了。

**以下手工路径适合**：想精确控制每个字段 / AI 铸的不满意 / 团队要评审模板设计。

## 一、先建立心智模型（3 分钟）

元铸工坊的核心思想：**给你的工作世界建模**，然后 AI 在模型里干活、人把关。

四段式模板 = 一个领域的完整描述：

| 段 | 是什么 | 类比 |
|----|--------|------|
| ① 对象模型 | 你的工作里有哪些"名词"（实体+属性+关系） | 数据库表设计 |
| ② 动作库 | 这些名词上允许哪些"动词"（写操作，带校验） | API 接口 |
| ③ 工作流 | 动词+AI 步骤怎么串成一条流程 | 自动化脚本 |
| ④ 评测集 | 怎么验收这条流程没坏 | 单元测试 |

**AI 提议、人拍板**：工作流里 AI 产生的所有写操作默认进待审中心，你批准才生效。

## 二、5 步做一个模板（真实例子：会议纪要域）

我们做一个「会议追踪」模板：登记会议 → AI 从会议描述提炼行动项 → 行动项进待审中心。

### Step 1：建目录骨架

```
templates/meeting/
├── manifest.yaml          # 模板身份
├── ontology/
│   ├── object-types.yaml  # ① 名词
│   └── link-types.yaml    # ① 名词间关系（可省）
├── actions/               # ② 动词（每文件一个）
│   ├── create-meeting.yaml
│   └── create-action-item.yaml
├── workflows/             # ③ 流程
│   └── extract-actions.yaml
└── evals/
    └── cases.yaml         # ④ 验收
```

### Step 2：写 manifest（模板身份）

```yaml
name: meeting
version: 0.1.0
domain: meeting            # 领域名（小写英文，MCP 工具名会用到）
description: 会议追踪——登记会议、AI 提炼行动项、人审后入库
```

### Step 3：定义你的名词（object-types.yaml）

想清楚你工作里的名词和每个名词的属性：

```yaml
types:
  - name: Meeting                          # 会议
    title_key: title
    exposed: true                          # 暴露后 agent 可经 MCP 查询
    properties:
      title: {type: string, required: true}
      date: {type: string}
      attendees: {type: string}
      raw_notes: {type: string}            # 会议原始记录

  - name: ActionItem                       # 行动项
    title_key: title
    exposed: true
    properties:
      title: {type: string, required: true}
      owner: {type: string}                # 负责人
      due: {type: string}                  # 截止
      status: {type: string, enum: [Open, Done], default: Open}
```

**字段说明**：`required` 必填；`enum` 限定取值；`default` 默认值；`title_key` 指定哪个属性当显示标题。

### Step 4：定义动词（actions/*.yaml）

每个写操作一个文件。**这是治理的核心**——AI 只能做这里声明过的动作：

```yaml
# actions/create-action-item.yaml
name: CreateActionItem
description_for_agent: 创建一条行动项（进入待审中心等人确认）   # agent 看到的说明
autonomy_level: 2          # 2=需要人审；1=自动执行（只用于低风险操作）
requires_staging: true     # 写操作默认 true
idempotency_key_template: "ai-{title}"   # 防重复提交
params:                    # 参数格式约束
  type: object
  properties:
    title: {type: string}
    owner: {type: string}
    due: {type: string}
  required: [title]
transform:                 # 批准后实际做什么：建对象
  - create_object:
      type: ActionItem
    with:
      title: from:params.title        # 从参数取
      owner: from:params.owner
      due: from:params.due
      status: literal:Open            # 固定值
```

**transform 两种规则**：
- `create_object`：建新对象（`from:params.x` 取参数，`literal:值` 固定值）
- `set`：改现有对象属性（`{"set": "properties.status", "value": Done}`）

**进阶——运行时校验**（比如"只有 Open 状态的行动项能完成"）：

```yaml
submission_criteria:
  object_ref: params.object_id
  check: {properties.status: Open}
```

### Step 5：串工作流（workflows/extract-actions.yaml）

```yaml
name: extract-actions
description: 从会议记录提炼行动项（AI 起草，人审后入库）
params_schema:                       # 使用者填什么（Web 弹窗/CLI --param）
  - name: meeting_title
    label: 会议标题
    type: string
    required: true
  - name: raw_notes
    label: 会议记录（粘贴进来）
    type: text
    required: true
steps:
  - id: extract
    type: ai_step                    # AI 步骤
    prompt_prefix: |                 # 稳定前缀（角色+规则，别放变量）
      你是会议助理。从会议记录中提取所有行动项。
      严格按 JSON 数组输出，每项 {"title": "...", "owner": "...", "due": "..."}。
      没有行动项就输出 []。不要输出其他文字。
    prompt_var: raw_notes            # 可变段（绑定使用者输入）
    model: glm-5.1                   # 任意已配置模型（yuanzhu mcp tools 可查）
    output: candidates
    expect_json: true                # 期望 JSON 输出

  - id: submit
    type: action_step                # 动作步骤
    action: CreateActionItem
    iterate_over: candidates         # 逐条执行（每条都进待审中心）
    params:
      title: $item.title
      owner: $item.owner
      due: $item.due
```

**三种步骤**：`ai_step`（调模型）/ `action_step`（做动作）/ `query_step`（查对象）。
**变量绑定**：`$params.x`（使用者输入）/ `$item.x`（迭代项）/ `$上游output名`。

### Step 6：写验收用例（evals/cases.yaml）

```yaml
cases:
  - name: 建会议-自动生效
    steps:
      - action: CreateMeeting
        params: {title: 周会, date: "2026-09-10"}
    expect: {status: applied, object_exists: {type: Meeting, title: 周会}}

  - name: 建行动项-人审后入库
    steps:
      - action: CreateActionItem
        params: {title: 补齐文档, owner: 小李}
        expect: {status: staged}
      - approve: {}
    expect: {status: applied, object_exists: {type: ActionItem, title: 补齐文档}}
```

## 三、注册与验证

```bash
# 启动中控后
yuanzhu templates                                    # 确认服务在线
# 注册（路径必须在仓库 templates/ 之下）
#   方式一：CLI 管理员代发 HTTP（见下）
#   方式二：curl/python POST /api/templates/register {"path": "templates/meeting"}

# 跑评测（四段式验收）
#   EvalsRunner 走 python -m pytest 或经 API 触发

# Web 验证：打开模板市场 → 你的模板 → 点「使用」
yuanzhu mcp tools        # agent 端可见 query_meeting_meeting / execute_meeting_createactionitem
```

## 四、调试心法

| 症状 | 查什么 |
|------|--------|
| 注册报 YAML 错 | manifest 缺 name/version/domain；YAML 缩进 |
| 工作流跑挂 | ai_step 的模型名（`yuanzhu mcp tools` 查可用模型）；expect_json 的输出不是数组 |
| 动作被拒 | params 不合 schema；submission_criteria 的状态不满足 |
| 待审中心看不到产出 | 该动作 autonomy_level=1（自动执行了，不进待审） |

## 五、设计纪律（四条，违反必踩坑）

1. **从真实工作出发**：先写下你每天重复做的事，再挑高频的建模——别凭空设计
2. **确定性转换不用 AI**：改状态、算数值用 `set` 规则；AI 只用于理解/生成/判断类步骤
3. **写操作默认人审**（autonomy 2）；只把无风险的登记类设为 1（自动）
4. **三次重复再抽象**：先做最小模板跑通一条流，别一开始就设计大而全
